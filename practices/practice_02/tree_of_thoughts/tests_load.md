# Нагрузочные проверки

Ниже «карточки» сценариев и пороги для сервиса AI‑помощника ревьюера PR. Они опираются на CASE.md (SEC-1, API-1, REL-1, OUT-1, QA-1, OBS-1) и проверяются на локальном стенде.

## Сценарии

### Сценарий 1. Прогрев → полка → охлаждение (REL-1)
- Профиль нагрузки: прогрев 0→50 VU за 2 мин; полка 5 мин (rps≈100); охлаждение 2 мин. Длина diff ≈ 8k. LLM‑заглушка: 300 мс.
- Метрики и пороги: клиент — 5xx < 0.5%, p95 < 900 мс, p99 < 1200 мс; ресурсы — CPU avg на полке < 70%, пик < 85%; RSS < 400 МиБ; GC паузы p95 < 50 мс.
- Шаги запуска: подготовить стенд и заглушку (см. «Методика и окружение»); запустить k6 с `VUS=50 DUR=5m LEN=8000`.
- Evidence: отчёт k6 (latency, коды), системные метрики через /metrics или `docker stats` с 1‑с сэмплированием. Ссылка на правило: CASE.md: REL-1.

### Сценарий 2. Порог длины диффа (API-1)
- Профиль нагрузки: размеры diff 5k, 10k, 20k, 30k; по 10 запросов на уровень, пауза 100 мс.
- Метрики и пороги: при len≤20k — 2xx ≥ 99%, p95 < 800 мс; при len>20k — 413 = 100%, вызов внешнего LLM = 0. Ресурсы: CPU avg < 75%, прирост RSS на шаг < 50 МиБ.
- Шаги запуска: для проверки порога выполнить `LEN=19000 k6 run k6_review.js` и `LEN=21000 k6 run k6_review.js`.
- Evidence: HTTP‑коды и латентность из k6, счётчик вызовов LLM‑заглушки, CPU/RSS процесса/контейнера. CASE.md: API-1.

### Сценарий 3. Всплеск параллелизма (spike) (REL-1)
- Профиль нагрузки: 0 VU → 100 VU на 60 с → 0 VU. LLM‑заглушка: 300 мс.
- Метрики и пороги: ошибки < 1%; p99 < 1500 мс; время восстановления до p95<900 мс после всплеска < 30 с; CPU пик ≤ 90% не дольше 10 с; таймауты = 0.
- Шаги запуска: k6 stages со всплеском; задать профиль в `options` или переменных окружения.
- Evidence: клиентские метрики k6, фиксация времени восстановления p95; системные — как в сценарии 1. CASE.md: REL-1.

### Сценарий 4. Таймаут/деградация внешнего LLM (REL-1, OUT-1)
- Профиль нагрузки: 10 VU, 2 мин. LLM‑заглушка задержка 12 с. Таймаут сервиса: 10 с.
- Метрики и пороги: 504 с предсказуемым телом; доля 504 = 100%; нет 500/502; время ответа сервиса < 11 с; ресурсы стабильны (CPU avg < 40%, RSS без тренда роста).
- Шаги запуска: `export LLM_DELAY_MS=12000; VUS=10 DUR=2m LEN=8000 k6 run k6_review.js`.
- Evidence: коды/тело ответа, отсутствие зависаний и ростов памяти; латентность клиента и системные метрики. CASE.md: REL-1, OUT-1.

### Сценарий 5. Редакция секретов и логи (SEC-1, OBS-1, QA-1)
- Профиль нагрузки: 20 VU, 1 мин; в каждом diff включён токен `sk_test_...`.
- Метрики и пороги: утечки секретов = 0 по regex; в промпте/логах вместо токена — `[REDACTED]`; в логах только request_id, длительность, статус; на 1000 req объём логов < 5 МиБ; нагрузка редактирования: +CPU ≤ 5 п.п. к сценарию 1.
- Шаги запуска: отправлять diff со строкой `token=sk_test_123`; сравнить CPU с базовой полкой (сценарий 1).
- Evidence: парсинг логов и промптов к LLM; отчёт k6; сравнение CPU. CASE.md: SEC-1, OBS-1, QA-1.

Примечание: если нагрузочное тестирование пока не требуется, это допустимо только при отсутствии пользовательского трафика и до появления внешнего API. Условие включения — первый интеграционный стенд с внешним LLM или SLA для ответа.

## Методика и окружение

- Стенд: локально, сервис на http://localhost:8080. Внешний LLM — заглушка на http://localhost:9090.
- Данные: `practices/practice_01/TRAINING_PR.diff` как базовый diff; генератор добавляет паддинг под целевую длину.
- Инструменты: k6 v0.49+, curl 7.88+, Python 3.11+ (заглушка), jq (валидация логов), Docker 24+ или Prometheus /metrics.
- Конфигурация LLM‑заглушки: `LLM_DELAY_MS=300` (базово) и `LLM_DELAY_MS=12000` (таймаут).
- Сбор метрик: клиентские — отчёт k6 (latency p95/p99, коды, ошибки); системные ресурсы — либо Prometheus /metrics сервиса (`process_cpu_seconds_total`, `process_resident_memory_bytes`, `*_gc_*`), либо `docker stats --no-stream` с 1‑с сэмплированием. Если GC недоступен — помечаем GC=N/A и фиксируем причину.
- Агрегация: для p95/p99 — медиана из 3 прогонов; для CPU/RSS — среднее и пик на полке; для GC — p95 на полке.
- Повторы и seed: каждый сценарий — 3 прогона. Для генераторов используем фиксированный `seed=42` (если применимо). Профили k6 фиксированы в сценариях.
- Артефакты: сохраняем raw‑логи k6, сервисные логи, выгрузку метрик/`docker stats` и конфиг стенда.

Пример k6 (сокращённый):

```js
// save as k6_review.js
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = { vus: __ENV.VUS || 10, duration: __ENV.DUR || '1m' };

function genDiff(target) {
  const base = 'diff --git a/a b/b\n';
  const pad = 'x'.repeat(Math.max(0, target - base.length));
  return base + pad;
}

export default function () {
  const len = Number(__ENV.LEN || 10000);
  const res = http.post('http://localhost:8080/review', genDiff(len), {
    headers: { 'Content-Type': 'text/plain' },
  });
  check(res, { 'status ok or 413': r => [200, 201, 202, 413].includes(r.status) });
  sleep(0.1);
}
```

Минимальная заглушка внешнего LLM (Python):

```python
# llm_stub.py
from http.server import BaseHTTPRequestHandler, HTTPServer
import os, time

class H(BaseHTTPRequestHandler):
    def do_POST(self):
        delay = int(os.getenv('LLM_DELAY_MS', '300')) / 1000.0
        time.sleep(delay)
        self.send_response(200)
        self.end_headers()
        self.wfile.write(b'{"ok": true}')

HTTPServer(('0.0.0.0', 9090), H).serve_forever()
```

## Как использовали AI

- Техника: Tree of Thoughts (внешние альтернативы). Сформировали три альтернативы подачи материала: A — «Матрица сценариев», B — «Карточки сценариев», C — «Маппинг требований→тесты».
- Критерии: проверяемость, воспроизводимость, полнота, ясность, соответствие README.md.
- Выбор: B («Карточки») — максимальная ясность и воспроизводимость при сохранении полноты. Внесли явные шаги запуска и список evidence.
- Что отклонили: А (компактно, но мало шагов) и C (хорошая трассируемость, но недостаточно конкретики для запуска).
