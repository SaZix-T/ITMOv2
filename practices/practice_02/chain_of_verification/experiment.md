## Методика и окружение

- Стенд: локально, сервис на http://localhost:8080. Внешний LLM — заглушка на http://localhost:9090.
- Данные: `practices/practice_01/TRAINING_PR.diff` как базовый diff; генератор добавляет паддинг под целевую длину.
- Инструменты: k6 v0.49+, curl 7.88+, Python 3.11+ (заглушка), jq (валидация логов), Docker 24+ или Prometheus node_exporter/экспозиция /metrics у сервиса.
- Конфигурация LLM-заглушки: `LLM_DELAY_MS=300` (базово) и `LLM_DELAY_MS=12000` (таймаут).
- Сбор метрик: клиентские — из отчёта k6 (latency p95/p99, коды, ошибки). Системные ресурсы — один из вариантов: 1) Prometheus /metrics сервиса: `process_cpu_seconds_total`, `process_resident_memory_bytes`, `*_gc_*` (go/node); 2) обёртка сервиса в контейнер и `docker stats --no-stream` с 1-сек сэмплированием. Если GC недоступен — помечаем GC=N/A и фиксируем причину.
- Агрегация: для p95/p99 — медиана из 3 прогонов; для CPU/RSS — среднее и пик на полке; для GC — p95 на полке.
- Повторы и seed: каждый сценарий — 3 прогона. Для генераторов используем фиксированный seed=42 (если применимо). Профили k6 (stages) фиксированы в сценариях.
- Отчётность: сохраняем raw-логи k6, сервисные логи, выгрузку метрик/`docker stats` и конфиг стенда в артефакты прогона.
