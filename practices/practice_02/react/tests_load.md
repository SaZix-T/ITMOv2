# Нагрузочные проверки

Ниже сценарии и пороги для сервиса AI-помощника ревьюера PR. Они опираются на CASE.md (SEC-1, API-1, REL-1, OUT-1, QA-1, OBS-1) и проверяются на локальном стенде.

## Сценарии

| Сценарий | Профиль нагрузки и длительность | Метрики и целевые пороги | Что и как измеряем | Evidence |
|---|---|---|---|---|
| 1) Прогрев → полка → охлаждение (REL-1) | Прогрев 0→50 VU за 2 мин; полка 5 мин (rps≈100); охлаждение 2 мин. LLM‑заглушка 300 мс; длина diff ≈ 8k | 5xx < 0.5%; p95 < 900 мс; p99 < 1200 мс; CPU avg на полке < 70%, пик < 85%; RSS < 400 МиБ | k6 stages; клиентские метрики из отчёта k6; системные — /metrics или `docker stats` с 1‑с сэмплированием | CASE.md: REL-1 |
| 2) Порог длины диффа (API-1) | Размеры diff 5k, 10k, 20k, 30k; по 10 запросов на уровень, пауза 100 мс | При len≤20k: 2xx ≥ 99%, p95 < 800 мс; при len>20k: 413 = 100%, вызов внешнего LLM = 0 | Формируем diff нужной длины; POST /review; фиксируем HTTP‑коды, латентность и счётчик обращений к LLM‑заглушке | CASE.md: API-1 |
| 3) Таймаут внешнего LLM (REL-1, OUT-1) | 10 VU, 2 мин; `LLM_DELAY_MS=12000` при таймауте сервиса 10 с | Доля контролируемых ответов 504 = 100%; 5xx = 0; время ответа сервиса < 11 с | Имитируем превышение таймаута; проверяем коды/тело ответа и отсутствие зависаний | CASE.md: REL-1, OUT-1 |

Примечание: если нагрузочное тестирование пока не требуется, это допустимо только при отсутствии пользовательского трафика и до появления внешнего API. Условие включения — первый интеграционный стенд с внешним LLM или SLA на ответ.

## Методика и окружение

- Стенд: локально, сервис на http://localhost:8080. Внешний LLM — заглушка на http://localhost:9090.
- Данные: `practices/practice_01/TRAINING_PR.diff` как базовый diff; генератор добавляет паддинг под целевую длину.
- Инструменты: k6 v0.49+, curl 7.88+, Python 3.11+ (заглушка), jq (валидация логов), Docker 24+ или Prometheus /metrics.
- Конфигурация LLM‑заглушки: `LLM_DELAY_MS=300` (базово) и `LLM_DELAY_MS=12000` (таймаут).
- Повторы: каждый сценарий — 3 прогона; для p95/p99 берём медиану; системные метрики — среднее и пик на полке.
- Артефакты: сохраняем raw‑логи k6, сервисные логи, выгрузку метрик/`docker stats` и конфиг стенда.

Пример k6 (сокращённый):

```js
// k6_review.js
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = { vus: __ENV.VUS || 10, duration: __ENV.DUR || '1m' };

function genDiff(target) {
  const base = 'diff --git a/a b/b\n';
  const pad = 'x'.repeat(Math.max(0, target - base.length));
  return base + pad;
}

export default function () {
  const len = Number(__ENV.LEN || 10000);
  const res = http.post('http://localhost:8080/review', genDiff(len), {
    headers: { 'Content-Type': 'text/plain' },
  });
  check(res, { 'status ok или 413': r => [200, 201, 202, 413].includes(r.status) });
  sleep(0.1);
}
```

Команды запуска (примеры):

```bash
# Сценарий 2: порог по длине
LEN=19000 k6 run k6_review.js
LEN=21000 k6 run k6_review.js

# Сценарий 1: полка 50 VU, 5 минут
VUS=50 DUR=5m LEN=8000 k6 run k6_review.js

# Сценарий 3: таймаут внешнего LLM
export LLM_DELAY_MS=12000
VUS=10 DUR=2m LEN=8000 k6 run k6_review.js
```

## Как использовали AI

- Техника: ReAct (действия + наблюдения). Работали итеративно: Analyze текущих файлов (README.md, CASE.md, черновик tests_load.md) → Propose фрагменты таблицы и секций → Validate соответствие правилам и проверяемость.
- Из предложений выбрали 4 сценария, перекрывающие правила API-1, REL-1, OUT-1, SEC-1, OBS-1. Пороги увязали с учебным стендом и сделали воспроизводимыми (k6, заглушка LLM).
- Отклонённые варианты: стресс 500 VU, p99<200 мс без обоснования, нерелевантные сценарии (i18n/БД) и расплывчатые формулировки «быстро/медленно».
