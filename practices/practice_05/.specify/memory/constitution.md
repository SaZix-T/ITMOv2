# TaskFlow Constitution

## Core Principles

### I. Слоистая архитектура и только подготовленные SQL-запросы
Маршруты (`src/routes/*`) занимаются только HTTP: валидируют вход, вызывают функции слоя данных и возвращают JSON. Весь SQL живёт в `src/db.js` и выполняется исключительно через prepared statements с `?` или `@name` плейсхолдерами. Интерполяция значений в SQL запрещена. Фабрика `createDb(dbPath)` принимает путь к базе и не знает о Express.

### II. Явная валидация и единый формат ошибок
Каждый обработчик маршрута валидирует вход и возвращает ошибку в виде `{ "error": "message" }` с корректным HTTP-статусом (400 — невалидный вход, 404 — ресурс не найден, 500 — внутренняя ошибка). Параметры пути приводятся через `Number()`. Асинхронные обработчики оборачиваются общим `asyncHandler`, чтобы ошибка попадала в централизованный обработчик, а не терялась в промисах.

### III. Фронтенд без фреймворка и без прямых связей с БД
Клиент — ванильный JavaScript: `document.getElementById`, `addEventListener`, `innerHTML`. Все сетевые вызовы идут через единственный хелпер `api(path, opts)`, который проверяет `res.ok` и бросает ошибку с текстом из тела ответа. Рендер списка — полная перерисовка из массива `tasks[]`, без точечных правок DOM. Пользовательский текст экранируется функцией `esc()` перед вставкой в `innerHTML`. У списка есть три состояния: загрузка, пусто, ошибка.

### IV. Тесты — условие готовности (NON-NEGOTIABLE)
Тест-раннер — встроенный `node:test` + `node:assert`, без Jest и других зависимостей. Слой данных тестируется на временной БД через фабрику, HTTP-слой — на живом сервере с подменой `PORT` и `DB_PATH`. Любая фича считается сделанной только при `npm test` с нулём падений. Ослаблять или удалять существующие проверки, чтобы получить зелёный прогон, запрещено.

### V. Простота и отсутствие лишних зависимостей
Стек фиксирован: Express + better-sqlite3 + ванильный фронтенд. Новые npm-зависимости, TypeScript, сборка и фронтенд-фреймворки не добавляются. Изменения схемы БД делаются идемпотентно (`CREATE TABLE IF NOT EXISTS` + `ALTER TABLE ... ADD COLUMN` в защищённом блоке), как это уже сделано для `due_date`, и не ломают существующие данные.

## Технологические ограничения

- Runtime: Node.js >= 18, SQLite через `better-sqlite3`, журнал WAL.
- Статика отдаётся `express.static` из `public/`; API — префикс `/api/tasks`.
- Данные разработчика (`data/taskflow.db`) не используются в тестах и проверках: тесты и `scripts/verify.sh` работают на отдельных файлах БД и отдельных портах.
- Формат даты в интерфейсе и API — ISO-8601 (`YYYY-MM-DD` либо `datetime('now')` в SQLite).

## Процесс разработки и контроль качества

- Источник правил для агента — `AGENTS.md`; конституция задаёт принципы, которым эти правила обязаны соответствовать.
- Definition of Done: `npm test` выходит с кодом 0; `node server.js` поднимается; `GET /` отдаёт HTML; `GET /api/tasks` отдаёт валидный JSON-массив.
- Полная проверка перед объявлением работы завершённой — `bash scripts/verify.sh` (тесты + живой сервер на скретч-порту).
- Каждая фича проходит путь спецификация → план → задачи → реализация; расхождение кода со спецификацией исправляется в спецификации, а не в обход неё.

## Governance

Конституция важнее текущих привычек и подсказок агента; при конфликте выигрывает она. Поправки вносятся только явным решением владельца проекта, с повышением версии по семантическим правилам и датой изменения. Каждая фича проверяется на соответствие этим принципам на этапах плана и анализа; сложность, нарушающая принцип V, требует отдельного обоснования. `AGENTS.md` остаётся практическим руководством по среде и командам.
