# Research: Статистика выполненных задач

**Feature**: `002-completion-stats` | **Date**: 2026-10-27

## Вопросы и решения

### R1. Откуда брать момент выполнения

**Решение**: новая колонка `completed_at TEXT DEFAULT NULL` в `tasks`. Заполняется `datetime('now')` при переходе `completed 0 → 1`, обнуляется при обратном переходе. Для уже выполненных строк при миграции проставляется `updated_at` (допущение из спецификации).

**Обоснование**: статистика по «сегодня/вчера» невозможна без метки времени; поле принадлежит задаче, отдельная таблица событий избыточна для личного менеджера (принцип V). SQLite-функция `datetime('now')` уже используется проектом для `created_at`/`updated_at`, значит формат хранения совпадает и сравнения строк работают лексикографически.

**Отброшено**: отдельная таблица `completion_events` (даёт историю многократных выполнений, но требует join и чистки при удалении задач — сверх задачи); вычисление по `updated_at` без нового поля (ломается при любом редактировании выполненной задачи).

### R2. Как считать «сегодня» и «вчера» в нужном часовом поясе

**Решение**: хранить время в UTC, а группировать в SQL через `date(completed_at, 'localtime')`; границы — `date('now', 'localtime')` и `date('now', 'localtime', '-N days')`.

**Обоснование**: `datetime('now')` в SQLite всегда UTC. Приведение к локальной дате на стороне SQL даёт корректные календарные дни сервера (допущение спецификации) и не требует хранения пояса в каждой строке. Строковые даты `YYYY-MM-DD` сравниваются лексикографически, поэтому `>=` по `date(...)` эквивалентен сравнению дат.

**Отброшено**: хранение локального времени в колонке (сломается при смене пояса и DST); расчёт в JS после выборки всех задач (лишний объём и дублирование логики).

### R3. Форма ответа API статистики

**Решение**: `GET /api/stats/completed` → `{ today, yesterday, last7Days, last30Days, daily: [{ date, count } x 30] }`, где `daily` — непрерывный ряд от 29 дней назад до сегодня, нули включены.

**Обоснование**: один запрос отдаёт и сводку, и ряды для двух графиков; непрерывность ряда обеспечивается сервером, чтобы клиент не «додумывал» пропущенные дни (FR-007/FR-008/FR-009). Суммы считаются из того же ряда, что и столбцы, поэтому расхождение чисел и графиков невозможно.

**Отброшено**: два раздельных эндпоинта (лишний round-trip), отдача только сводки (клиент не смог бы построить график без второго запроса).

### R4. Где считать агрегаты

**Решение**: в `src/db.js` функция `statsCompleted()` одним SQL-запросом `GROUP BY date(completed_at,'localtime')` по окну 30 дней; маршрут `src/routes/stats.js` только сериализует результат. Дополнение отсутствующих дней нулями — в `db.js`, чтобы контракт был стабильным.

**Обоснование**: принцип I — весь SQL в слое данных; маршрут не должен знать про даты. 30 строк — пренебрежимо малый объём, поэтому агрегация в SQL, а не в JS.

### R5. Как рисовать графики без библиотеки

**Решение**: инлайновый SVG, генерируемый строками в `public/app.js`: 7 столбцов для недельного графика и 30 узких столбцов для месячного, плюс подписи дат и значения над столбцами. Высота столбца — `count / max * height`, при `max = 0` все столбцы получают минимальную высоту 2px (защита от деления на ноль).

**Обоснование**: принцип III/V запрещают фронтенд-фреймворки и новые зависимости; SVG масштабируется, доступен для скринридеров через `role="img"` + `aria-label`, и не требует canvas-логики.

**Отброшено**: canvas (нет доступа к тексту и accessibility), Chart.js (новая зависимость), CSS-бары на flex (хуже с подписями и осями).

### R6. Как переключать вкладки без роутера

**Решение**: два блока в `index.html` (`#tasks-view`, `#stats-view`), кнопки вкладок с `aria-selected`, состояние `currentView` в `app.js`; при открытии статистики данные перезапрашиваются, при возврате к задачам список перерисовывается из уже загруженного массива.

**Обоснование**: SPA без фреймворка и без URL-роутинга — как устроен текущий проект. Перезапрос при каждом открытии выполняет FR-013.

### R7. Что делать со старыми выполненными задачами

**Решение**: одноразовый `UPDATE tasks SET completed_at = updated_at WHERE completed = 1 AND completed_at IS NULL` сразу после миграции колонки.

**Обоснование**: иначе статистика на существующих данных всегда нулевая. `updated_at` — ближайшая доступная метка к моменту выполнения; допущение зафиксировано в спецификации. Запрос идемпотентен: после первого запуска условие `IS NULL` уже не срабатывает.
