# Research: Приоритеты задач

**Feature**: `001-priority-flags` | **Date**: 2026-10-27

## Вопросы и решения

### R1. Где хранить приоритет

**Решение**: новое целочисленное поле `priority` в существующей таблице `tasks`, значение 1–4, по умолчанию 1.

**Обоснование**: приоритет — атрибут одной задачи, отдельная таблица не нужна. Конституция (принцип V) требует идемпотентной миграции тем же способом, каким в проект уже добавлен `due_date`: `ALTER TABLE tasks ADD COLUMN` в `try { } catch {}`. `ALTER TABLE ... ADD COLUMN priority INTEGER NOT NULL DEFAULT 1` в SQLite допустим и проставляет 1 всем существующим строкам, поэтому старые задачи совместимы без скрипта миграции.

**Отброшено**: отдельная таблица `task_priority` (лишнее соединение ради одного скаляра); `TEXT`-значение приоритета (сравнения и валидация усложняются без выгоды).

### R2. Где валидировать диапазон 1–4

**Решение**: в двух местах: маршрут отклоняет некорректный вход с `400 { error }`, слой данных нормализует значение при чтении (`1..4`, иначе 1).

**Обоснование**: принцип II требует явной валидации на границе HTTP и единого формата ошибок; принцип I запрещает SQL в маршрутах, поэтому проверка диапазона живёт рядом с запросами. Нормализация при чтении закрывает данные, попавшие в базу в обход API (например, старые файлы или ручные правки), и обеспечивает FR-008/FR-009.

### R3. Как реализовать меню выбора приоритета без фреймворка

**Решение**: состояние `openPriorityId` в модуле `app.js`; при отрисовке задачи с открытым меню внутрь карточки добавляется блок с четырьмя кнопками. Закрытие — обработчик `click` на `document` (если клик вне `.priority-menu`) и `keydown` на `Escape`.

**Обоснование**: проект рендерит список полной перерисовкой (принцип III), поэтому меню — часть состояния рендера, а не отдельный DOM-виджет с ручным позиционированием. Никаких новых зависимостей (принцип V).

**Отброшено**: нативный `<select>` (не даёт цветных вариантов и одинаково выглядит во всех ОС), библиотека popover (новая зависимость), циклическое переключение по клику (заказчик выбрал меню в `/speckit.clarify`).

### R4. Как показать цвет приоритета

**Решение**: CSS-переменные `--prio-1..4` и модификатор `.priority-flag[data-priority="N"]`; иконка — инлайновый SVG-флажок с `fill: currentColor`.

**Обоснование**: цвета заданы постановкой: 1 — серый `#9ca3af`, 2 — синий `#4dabf7` (совпадает с акцентом проекта), 3 — оранжевый `#f59e0b`, 4 — красный `#ef4444` (совпадает с `--danger`). Инлайновый SVG не требует внешних ассетов и шрифтов, масштабируется и наследует цвет через `currentColor`. Выполненные задачи не приглушают флажок (FR-012): правило `.task-item.completed .priority-flag` не задаёт opacity.

### R5. Порядок списка

**Решение**: оставить `ORDER BY created_at DESC` без изменений; сортировки по приоритету нет.

**Обоснование**: подтверждено заказчиком при уточнении; FR-010 и SC-005 требуют неизменности порядка, а изменение порядка затронуло бы существующие тесты и ожидания пользователя.

### R6. Как проверить фичу

**Решение**: расширить `test/db.test.js` и `test/api.test.js` (значение по умолчанию, сохранение, границы 1 и 4, отказ для 0/5/строки), затем прогнать `bash scripts/verify.sh`. UI-часть проверяется вручную по quickstart.

**Обоснование**: в проекте нет DOM-тест-раннера и добавлять его запрещено принципом V; существующий контракт проверки — `node:test` + живой сервер. Поведение меню проверяется сценариями из quickstart на реальном сервере.
