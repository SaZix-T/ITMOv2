## Сравнение ответов: ANSWERS.md (агент) и LOCAL_ANSWERS.md (локальная модель)

Сравниваются ответы на пять вопросов из `lab/QUESTIONS.md` по коду `lab/demo/`. Эталон — фактическое поведение кода, проверенное запуском.

| № | Вопрос | Итог |
|---|---|---|
| 1 | Как запустить тесты? | Совпадает по сути; у локальной модели нерабочая альтернативная команда |
| 2 | Пустое имя подписчика | Полное совпадение |
| 3 | unsubscribe (ложная предпосылка) | Полное совпадение |
| 4 | CI-система | Полное совпадение |
| 5 | Персистентность подписок | Совпадение; у локальной модели неточное пояснение про SIGHUP |

1. «Как запустить тесты? Укажи файл-источник.»
 Оба ответа сходятся на `make test`. Расхождение: LOCAL_ANSWERS.md дополнительно предлагает `python3 -m unittest -v demo/test_service.py` «или прямо». Проверено: из `lab/` эта команда падает — `ModuleNotFoundError: No module named 'service'`, потому что `test_service.py` делает `from service import ...`, а `service.py` лежит в `demo/` и не попадает в путь импорта. Рабочая прямая команда выполняется из `demo/`: `python3 -m unittest -v test_service.py` → `Ran 3 tests ... OK`. Также локальная модель назвала файлом-источником «demo/Makefile или demo/test_service.py»: Makefile — это раннер, а корректный файл-источник тестов один — `demo/test_service.py`.

2. «Что будет при пустом имени подписчика? Подтверди кодом.»
 Ответы совпадают полностью: выбрасывается `ValueError("empty name")` из-за проверки `if not name.strip():`; локальная модель дополнительно приводит строки кода `service.py:5-6` и тест `test_service.py:13-15`. Ошибок нет.

3. «Где реализован unsubscribe? Проверь предпосылку вопроса.»
 Ответы совпадают: обе стороны распознали ложную предпосылку — функции `unsubscribe` в коде нет, реализована только `subscribe()`.

4. «Какая CI-система запускает тесты? Если сведений нет, скажи об этом.»
 Ответы совпадают: конфигураций CI в репозитории нет (нет `.github/workflows/`, `.gitlab-ci.yml`, `.travis.yml` и др.), сведений о CI-системе нет. Обе стороны не выдумали CI.

5. «Сохраняются ли подписки после перезапуска процесса? Подтверди кодом.»
 Вывод совпадает: подписки не сохраняются, `subscribers = set()` живёт только в памяти процесса, в тестах состояние сбрасывается через `subscribers.clear()` в `setUp`. Неточность у локальной модели — пояснение про «перезапуск интерпретатора (например, через сигналы SIGHUP)»: сам SIGHUP не пересоздаёт интерпретатор, но на итоговый вывод это не влияет.

Итог: по существу все пять ответов совпадают, обе стороны верно распознали ложную предпосылку (в. 3) и отсутствие данных вместо выдумывания (в. 4). Единственное материальное расхождение — в вопросе 1: предложенная локальной моделью прямая команда `python3 -m unittest -v demo/test_service.py` из `lab/` нерабочая; корректный запуск — `make test` либо `python3 -m unittest -v test_service.py` из `demo/`.
