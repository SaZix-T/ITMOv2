Проблемы и риски
- app/api.py: отсутствие валидации входа и строгой схемы
- Код: def create_review(payload: dict) -> dict[str, str]: return review_service.review(payload["diff"])
- Риск: KeyError при отсутствии ключа "diff" → 500 вместо корректного 422.
- Рекомендация: использовать Pydantic-модель запроса (например, class ReviewRequest(BaseModel): diff: str) и объявить её в сигнатуре, что обеспечит автоматическую валидацию FastAPI.
- app/api.py: отсутствие обработки ошибок сервиса/LLM
- Если review_service.review или llm.generate бросит исключение (сетевые ошибки, таймауты), API вернёт 500 без понятного сообщения.
- Рекомендация: обернуть вызов в try/except, маппить ожидаемые ошибки в 4xx/5xx, логировать.
- app/api.py: потенциальная блокировка при синхронном вызове LLM
- Эндпоинт синхронный, llm.generate может быть блокирующим (сетевой I/O). При высокой нагрузке возможна блокировка воркеров ThreadPool.
- Рекомендация: либо сделать эндпоинт async и использовать неблокирующий клиент, либо явно offload-ить в threadpool с контролем таймаутов/лимитов.
- app/api.py / app/review_service.py: отсутствие ограничений на размер входного payload
- Большой diff может приводить к:
- Длинным запросам к LLM (дорого/медленно).
- Превышению лимитов токенов модели.
- Рекомендация: лимит на размер входа, усечение/сжатие, предварительная агрегация/суммаризация diff.
- app/api.py: отсутствие аутентификации/авторизации
- Новый POST /api/reviews открыт всем (если сервис публичный).
- Рекомендация: хотя бы базовое auth/ключи/ограничение по IP; rate limiting.
- app/review_service.py: уязвимость к prompt injection
- Строка: prompt = f"Review this pull request and find problems:\n{diff}"
- Риск: содержимое diff может навязать модели нежелательные инструкции.
- Рекомендация: явно отделять инструкции от данных (делимитеры), добавить строгие правила в system-промпт или слой санации, фильтровать/экранировать потенциально опасные инструкции.
- app/api.py: отсутствие схемы ответа и стабильного контракта
- Возвращается «сырой» dict[str, str] с ключом "comment". Без Pydantic-модели ответа OpenAPI будет неполным, а контракт — нестрогим.
- Рекомендация: описать ответную модель с полями и типами; предусмотреть расширяемость (например, список находок, уровни severity).
- app/api.py: зависимость через глобальный импорт, а не DI FastAPI
- from app.dependencies import review_service → сложно мока́ть и переопределять в тестах/на окружениях.
- Рекомендация: использовать Depends или внедрение через router.startup, возможность подмены в тестах.
- Совместимость версий Python
- Используются современные аннотации dict[str, str], Protocol. Требуется Python 3.9+ (для dict[...]) и 3.8+ для Protocol из typing.
- Если проект на 3.8 — dict[str, str] вызовет синтаксическую ошибку. Рекомендация: проверить версию рантайма; при необходимости заменить на Dict[str, str] из typing.
- app/review_service.py: «склейка» бизнес-логики и представления
- ReviewService.review возвращает уже JSON-структуру {"comment": answer}. Это связывает сервис с форматом API.
- Рекомендация: сервис пусть возвращает доменную сущность/строку, а API решает формат ответа.
- Документация/логирование/метрики
- Нет логов, нет описания промпта/правил, нет метрик по времени/ошибкам. Сложнее дебажить и поддерживать.
- Стиль/микро-замечания
- LLM Protocol: смена однострочного ... на многострочный вариант не несёт пользы, но допустима. Лучше придерживаться единого стиля.
- Нет докстрингов у публичных методов.
Открытые вопросы
- Какая версия Python в проде/CI? Это критично для dict[str, str].
- Предполагается ли публичный доступ к /api/reviews или это внутренний сервис?
- Какие лимиты по размеру diff/времени ответа ожидаются? Нужны ограничения?
- Какой SLA/ошибки считаются «ожидаемыми» для LLM? Нужна ли повторная попытка/дедупликация?
- Требуется ли локализация/формат отчёта (список находок с severity) вместо одной строки "comment"?
